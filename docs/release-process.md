# Версионирование и production-релизы

Production-версии backend следуют Semantic Versioning (`MAJOR.MINOR.PATCH`) и вычисляются автоматически из Conventional Commits — та же политика, что в plan-tuner (`scripts/release-version.sh` взят оттуда без изменения логики). Релизы выпускает только `master`; `dev` и `stage` деплоятся как раньше (образ `<SHA>`, без версий, тегов и Release).

## Источник истины

- **Аннотированные git-теги `vX.Y.Z`** этого репозитория. Тег создаётся только на коммите, который был развёрнут и проверен в production. Лёгкие (lightweight) теги и версии с ведущими нулями (`v1.0.08`) релизами не считаются и в расчёте версии не участвуют; лёгкий тег с именем выбранной версии блокирует публикацию (он не переносится).
- **GitHub Releases** — история релизов с заметками. `CHANGELOG.md` ведётся вручную, автоматика его не меняет.
- Образ релиза: `<DOCKERHUB_USERNAME>/ok-service-backend:X.Y.Z` (тег без `v`), метки `org.opencontainers.image.version` и `org.opencontainers.image.revision`.
- Литерал `1.0.3`, который раньше стоял в метрике `app_info`, точкой отсчёта не является и удалён.

## Conventional Commits

| Коммит | Повышение |
| --- | --- |
| `fix: OK-150 ...`, `perf: ...`, `fix(shifts): ...` | PATCH |
| `feat: OK-151 ...`, `feat(works): ...` | MINOR |
| `feat!: ...`, `fix(api)!: ...`, строка `BREAKING CHANGE:` или `BREAKING-CHANGE:` в теле | MAJOR |

`docs`, `chore`, `refactor`, `test`, `ci`, `build`, `style` и коммиты не по формату релиз не вызывают. Анализируются все коммиты после последнего тега без merge-коммитов, в том числе вошедшие через merge; применяется одно наибольшее повышение. Изменение, которое должно попасть в production (например, исправление Dockerfile), оформляйте как `fix:`.

Текст коммитов обрабатывается только как данные (`eval` не используется).

## Первый релиз 1.0.0

Пока в репозитории нет тегов `vX.Y.Z`, первый успешный production-прогон выпускает **ровно `1.0.0`** независимо от истории коммитов — даже если единственный новый коммит `ci: automate production releases`. Заранее ничего не тегируется: `v1.0.0` создаётся на коммите, который этот прогон развернул. Release помечается как «Initial production release».

Перед первым релизом:

1. Убедитесь, что в Docker Hub нет тега `1.0.0` у `ok-service-backend` (иначе прогон упадёт как конфликт).
2. Если в GitHub включены rulesets/защита тегов `v*`, разрешите создание тегов `github-actions[bot]`.
3. Production-сервер: `docker compose` и `git` в `apps/ok-service-backend`, checkout на `master` без локальных правок. `.release-state` ещё нет — появится после первого деплоя.

## Production-прогон

Весь прогон `master` сериализован (`concurrency: ok-service-backend-production`, без отмены выполняющегося): от выбора версии до публикации одновременно идёт только один. GitHub держит в группе один ожидающий прогон: новый ожидающий (в том числе повтор старого прогона) вытесняет прежний. Поэтому прогон, получивший `outdated`, ставит в очередь прогон вершины `master` (`release-ci.sh reschedule`, `gh workflow run`, право `actions: write` только у build-job), если вершина ещё не выпущена, — повтор старого прогона не может оставить вершину без деплоя.

1. **build-test-push**: тесты в Docker-образе `test` с PostgreSQL 14, затем `release-ci.sh select` определяет состояние:
   - `outdated` — `master` уже ушёл вперёд, а у этого коммита нет ни тега `vX.Y.Z`, ни образа `X.Y.Z` со своей ревизией (или коммит выпал из `master`, или уже есть релиз, которого нет в его истории): ничего не собирается и не деплоится, выпустит более новый прогон;
   - `none` — нет релизных коммитов: production-сборка, деплой и публикация пропускаются;
   - `released` — коммит уже помечен аннотированным `vX.Y.Z`: деплоя нет, публикация только дозавершается. Так же и после выхода более новой версии (см. «Публикация A после выхода B»): ни сборки (даже тестового образа), ни деплоя;
   - `resume` — образ `X.Y.Z` этого коммита уже есть и проходит **проверку идентичности**: переиспользуется. Это работает и когда `master` ушёл вперёд: прерванный релиз дозавершает тот прогон, который его начал, — решение принимается по registry и git, а не по выходам прошлой попытки;
   - `new` — собирается кандидат `<image>:master-<SHA>` (отдельный тег: dev/stage пишут `<SHA>`, а production-сборка того же коммита отличается `APP_VERSION`; target `prod`, OCI-метки, без provenance — один манифест), фиксируется его digest, тот же манифест получает тег `X.Y.Z` (`imagetools create --prefer-index=false`, без пересборки и без обёртки в index) и digest перепроверяется. Существующий `X.Y.Z` с тем же digest — успех без изменений.
   - Образ `X.Y.Z` с другими метками или другим digest — **ошибка** (не перезаписывается). «Образа нет» распознаётся только по ответу registry `not found`; ошибка доступа или сети останавливает прогон.
   - **Проверка идентичности** (`released`, `resume`, перепроверка в deploy и `publish`): метки `revision`/`version`, прочитанные по digest, равны SHA/версии; `X.Y.Z` и кандидат `master-<полный SHA>` разрешаются в **один и тот же** digest; в deploy и publish он же равен digest из сборки этого прогона. Нет кандидата, digest различаются (даже при правильных метках), метки не те или запрос к registry упал — ошибка до SSH, Alembic и публикации. Обычный обогнанный коммит без своего образа по-прежнему `outdated` (no-op).
2. **deploy**: перепроверка тем же `select`: коммит всё ещё в `master`, нет более нового релиза, состояние `resume`, версия и digest совпадают со сборкой. Затем по SSH выполняется `scripts/deploy-production.sh` из коммита прогона:
   - на `master` SSH-доступ к серверу настраивается, только если перепроверка разрешила деплой (`go=true`);
   - отказ, если `.release-state` на сервере содержит более новую версию или ту же версию другого коммита/образа;
   - отказ, если в checkout есть staged/unstaged изменения отслеживаемых файлов (они не трогаются; неотслеживаемые `.env`, `logs/`, `.release-state` допустимы); затем checkout переводится на коммит образа (`git merge --ff-only <SHA>`) и сверяется с ним — до Compose и Alembic;
   - образ скачивается по digest, тег `X.Y.Z` сверяется с ним;
   - `web` закрепляется за `<image>@sha256:…` файлом `.release-compose.yaml` (третий `-f` поверх `docker-compose.app.yaml` и `docker-compose.prod.yaml`; volumes и окружение не меняются). `services.web.image` из `docker compose … config --format json` (разбирается Python внутри проверенного образа, без сети; `config --images web` не подходит — он печатает и образы зависимостей) должен быть ровно этой ссылкой — иначе отказ **до** изменения `.env` и Alembic (в лог попадает только поле образа). Поэтому ошибочный `DOCKERHUB_USERNAME` на сервере не может запустить миграцию из чужого репозитория. Та же конфигурация используется для Alembic, перезапуска, проверки готовности и обоих прогревов;
   - в `.env` пишется `TAG=X.Y.Z` (для ручных команд без файла закрепления; если последняя строка `.env` без перевода строки, он добавляется — существующие записи не портятся);
   - `alembic upgrade head` → пересоздание `web` → проверка, что `web` запущен из образа с этим digest, и ожидание готовности (`/metrics` отвечает и `app_info` показывает `X.Y.Z`) → `rebuild-project-work-statistics` → `rebuild-project-material-statistics`;
   - только после всего этого атомарно записывается `.release-state`.
   Push worker на production не деплоится (только `dev`), `template-service` не трогается.
3. **publish** (`contents: write` только здесь; вход в Docker Hub — только для чтения при проверке идентичности): аннотированный тег `vX.Y.Z` на развёрнутом SHA и GitHub Release с версией, датой UTC, изменениями по группам (Breaking changes / Features / Bug fixes / Performance improvements), SHA, образом, digest и ссылкой на прогон.
4. **notify**: Telegram и комментарии Jira/OpenProject.

## Состояние на сервере

`apps/ok-service-backend/.release-state` (в `.gitignore`, в контейнер не монтируется):

```
VERSION=1.0.0
SHA=<коммит>
DIGEST=sha256:...
RUN_ID=<GitHub run id>
DEPLOYED_AT=2026-11-20T10:00:00Z
```

Файл означает «деплой завершён полностью»: миграции, перезапуск, проверки и оба прогрева статистики прошли. Повтор с теми же версией, SHA и digest проверяет, что `web` запущен из этого образа **и** готов (та же ограниченная по времени проверка `/metrics`), и только тогда сообщает `DEPLOY_RESULT=already-deployed` — без миграций и прогревов. Если контейнер этого образа не готов, деплой падает с явной ошибкой и публикация не выполняется. Если запущен другой образ — релиз разворачивается заново.

## Уведомления

| Итог | Когда |
| --- | --- |
| 🛑 Ошибка деплоя | упали тесты, сборка, выбор версии или деплой |
| ℹ️ Деплой не требуется | `outdated`, `none`, или перепроверка нашла коммит уже выпущенным. Jira/OpenProject не комментируются |
| ⚠️ Деплой подтверждён, релиз не опубликован | деплой прошёл, `publish` упал |
| ✅ Релиз vX.Y.Z выпущен | деплой (или ранее завершённый деплой) и публикация успешны |

`dev`/`stage` уведомляют как раньше («Деплой успешен» / «Ошибка деплоя»).

## Повторы и восстановление

«Re-run all jobs» — кнопка в GitHub Actions на странице прогона; выбор версии выполняется заново по тегам и registry, выходы прошлой попытки не нужны. «Re-run failed jobs» переиспользует выходы успешных job той же попытки.

| Ситуация | Что делать |
| --- | --- |
| Упали тесты или сборка до промоушена | Сервер и registry не менялись. Исправьте (`fix:`) или Re-run. |
| Промоушен прошёл (`X.Y.Z` в Docker Hub), прогон упал до тега | См. «Прерванный промоушен» ниже. |
| Упал деплой до `.release-state` | Re-run failed jobs того же прогона или Re-run all jobs (→ `resume`). Alembic пропускает применённые миграции, остальные шаги повторяются. |
| Деплой отказал: изменения отслеживаемых файлов в checkout сервера | Разберите их вручную (`git status` в `apps/ok-service-backend`), автоматика их не трогает, затем Re-run failed jobs. |
| Деплой отказал: `Compose resolves web to …` | Проверьте, что production-файлы Compose и `.release-compose.yaml` не переопределяют `web.image` иначе; `.env` и БД не менялись. Re-run failed jobs. |
| Повтор: `deployed but web is not ready` | Деплой завершён ранее, но контейнер сейчас не готов: публикация не выполнена. Восстановите `web` (`docker compose … logs web`), затем Re-run failed jobs — повтор без миграций и прогревов. |
| Деплой прошёл, упал `publish` (тега нет) | Production работает на проверенной `X.Y.Z`. Устраните причину (права токена, защита тегов), затем Re-run failed jobs того же прогона: `publish` создаст тег и Release. Re-run all jobs тоже подойдёт: сервер распознает завершённый деплой по `.release-state` и проверит готовность. |
| Тег создан, Release нет | Re-run failed jobs (или all jobs → `released`): `publish` создаёт Release, тег не трогает. Так же, если уже вышла более новая версия — см. «Публикация A после выхода B». |
| `… is sha256:X, not sha256:Y` / `master-<SHA> is missing` | Тег `X.Y.Z` и кандидат `master-<SHA>` указывают на разные сборки (или кандидата нет). Ничего не развёрнуто и не опубликовано. Выясните, какой digest действительно собран прогоном этого коммита; теги образов автоматика не переписывает. |
| Тег и Release есть | Повтор успешен без деплоя. Развернуть заново — только вручную. |
| `vX.Y.Z` существует на другом коммите | Ошибка: теги никогда не переносятся. Разберитесь вручную. |
| Попытка развернуть более старую ревизию | Отказ или no-op: `HEAD` не содержит последний тег, или на сервере `.release-state` новее. |

### Прерванный промоушен (A промоутирован, B уже в master)

Пример: прогон коммита **A** промоутировал образ `1.0.0` и упал до создания тега `v1.0.0`; затем в `master` пришёл **B** (`fix:`). Прогон B падает с `Image 1.0.0 … has revision=<A>`: B не забирает версию A.

1. Откройте **прогон A** (коммит — метка `org.opencontainers.image.revision` образа `1.0.0`) и нажмите **Re-run all jobs**. Выбор версии увидит: A всё ещё в `master`, релиза новее нет, образ `1.0.0` принадлежит A → `resume`; деплой, проверки и публикация `v1.0.0` на A.
2. После успеха откройте **прогон B** и нажмите **Re-run all jobs**: версия считается от `v1.0.0` → `1.0.1`.
3. Если A выпал из `master` (force-push) — A получит `outdated` и ничего не тронет. Удалять тег `1.0.0` в Docker Hub и перезапускать вершину можно, **только если production не менялся** прогоном A — проверьте по «Сверке сервера после прерванного деплоя» ниже: checkout сервера не на A, `.release-state` не упоминает `1.0.0`/A, `web` запущен не из образа A. Иначе сначала выполните сверку.

Прогон, который `master` обогнал и который ничего не промоутировал, всегда `outdated` (no-op). Повтор старого прогона после выхода более нового релиза — тоже `outdated`, если на его коммите нет своего аннотированного тега: production не откатывается, исторический тег не создаётся.

### Сверка сервера после прерванного деплоя

Нужна, если деплой упал после изменения сервера, а повтор того же прогона невозможен (коммит выпал из `master`) или отказывает. Ничего не удаляйте и не правьте `.release-state`, пока не сверены все пункты.

```bash
cd apps/ok-service-backend
git status --short && git log -1 --format='%H %s'            # checkout: какой коммит, есть ли правки
cat .release-state                                           # последний ЗАВЕРШЁННЫЙ деплой (если есть)
grep '^TAG=' .env; cat .release-compose.yaml                 # что Compose запустит
docker inspect -f '{{.Config.Image}} {{index .Config.Labels "org.opencontainers.image.revision"}} {{index .Config.Labels "org.opencontainers.image.version"}}' \
  $(docker compose -f docker-compose.app.yaml -f docker-compose.prod.yaml ps -q web)
docker compose -f docker-compose.app.yaml -f docker-compose.prod.yaml run --rm web alembic current
```

Что означают расхождения:

| Наблюдение | Значение и действие |
| --- | --- |
| checkout на A, `web` из прежнего образа, `alembic current` = head прежней версии | A упал до миграций: схема не менялась. Верните checkout на коммит из `.release-state` (`git checkout --detach <SHA>`, если A уже не в `master` — `git merge --ff-only` на новую вершину откажет), удалите тег `X.Y.Z` A в Docker Hub, перезапустите вершину. |
| `alembic current` новее, чем миграции прежней версии | Миграции A применены. Новая вершина должна содержать совместимые миграции (те же ревизии или их продолжение); иначе нужен ручной откат схемы (`alembic downgrade` образом A) — решение за разработчиком, автоматика схему не откатывает. |
| `web` запущен из образа A, `.release-state` без A | Деплой A прошёл перезапуск, но не завершился (готовность/прогревы). Production работает на неопубликованной версии: исправляйте вперёд новой вершиной (она развернётся поверх) или верните `web` на образ из `.release-state` (`docker compose … up -d web` с прежним `.release-compose.yaml`/`TAG`). |
| `.release-state` = A, но A не в `master` и тега нет | Деплой A завершён, публикация нет, а коммит убран из `master`. Новая вершина с той же версией упадёт («another commit»). Решите, остаётся ли A в production: если нет — разверните прежнюю версию вручную и только после этого замените `.release-state` содержимым, соответствующим фактически запущенному образу; если да — верните A в историю `master` и выполните Re-run. |

После сверки checkout сервера должен быть на коммите-предке новой вершины `master` без правок отслеживаемых файлов, иначе следующий деплой откажет до Compose.

### Прерванная публикация

- Тега нет, деплой подтверждён (`.release-state` содержит версию): Re-run failed jobs прогона, выполнившего деплой. Перед созданием тега `publish` проверяет, что коммит всё ещё в `master` (вершина может уйти вперёд); если `master` переписан и коммита там нет, тег не создаётся — см. сверку выше.
- Тег есть, Release нет: Re-run failed jobs или Re-run all jobs того же коммита (`released`): создаётся только Release.

### Публикация A после выхода B

Пример: прогон **A** развернул `1.0.0` и запушил аннотированный `v1.0.0`, но запрос к GitHub Release API упал. Затем **B** развернул и опубликовал `1.0.1`. Production остаётся на B.

1. Убедитесь, что `v1.0.0` аннотированный и указывает на A: `git fetch --tags origin && git cat-file -t v1.0.0` → `tag`, `git rev-parse 'v1.0.0^{commit}'` → SHA A.
2. Откройте **прогон A** и нажмите **Re-run failed jobs** (повторится только `publish` с выходами исходной сборки) или **Re-run all jobs** (`select` вернёт `released`: тестовая сборка, промоушен, deploy и reschedule пропускаются).
3. `publish` проверяет идентичность образа `1.0.0` (= `master-<A>`, метки A/1.0.0, digest сборки A) и создаёт **только** Release `v1.0.0` с заметками из диапазона A и digest A, с `make_latest=false` — `v1.0.1` остаётся последним релизом. Никаких сборок, промоушена, SSH, миграций, прогревов, деплоя и записи тегов.
4. Если Release уже есть — успех без изменений; повтор безопасен.

Отказы (ничего не меняется): тега `v1.0.0` нет (`A newer release v1.0.1 exists` — исторический тег не создаётся; full rerun → `outdated`), тег лёгкий или на другом коммите (`not an annotated tag` / `never moved`), образ не проходит проверку идентичности. Release создаётся, только если API ответил `404` на `releases/tags/v1.0.0`; любой другой ответ — ошибка.

## Версия во время работы

Production-образ собирается с `APP_VERSION=X.Y.Z` (build-arg → переменная окружения), метрика `app_info{version="X.Y.Z"}` показывает развёрнутую версию. Локально и на `dev`/`stage` — `dev`.

Проверка после релиза:

```bash
cd apps/ok-service-backend
cat .release-state
```

## Локальная проверка

`sh scripts/release-version.sh next` — версия для текущего `HEAD` (пусто — релизить нечего). Тесты `tests/test_release_automation.py` проверяют выбор версии, конфликты, проверку идентичности образа, публикацию (в том числе A после B), маршрутизацию job по `if:` из `deploy.yml` и серверный деплой на временной git-истории с подменёнными `docker`, `curl` и `git`; в CI они запускаются отдельным шагом в образе `test` (в нём есть `git` и `jq`) с `RELEASE_TESTS_REQUIRED=1`: отсутствие инструментов — ошибка, а не пропуск. Локально без `git`/`jq` git-часть пропускается.
