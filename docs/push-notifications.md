# Push-уведомления через Firebase

Документ описывает целевое расширение уведомлений в `ok-service-backend` по
образцу push-контура `ek-ls-backend`. Это описание архитектуры и порядка
реализации, а не утверждение, что push уже работает в этом сервисе.

## Что уже есть в `ok-service-backend`

Сохраняемые in-app уведомления реализованы отдельно от push:

- `app/domain/notifications` содержит сущности и правила уведомлений;
- `app/use_cases/notifications` содержит сценарии создания, чтения и фиксации
  просмотра;
- `app/adapters/notifications/sqlalchemy_repository.py` реализует PostgreSQL
  хранилище;
- `app/database/models/notifications.py` определяет общую запись уведомления и
  персональное состояние получателя;
- миграции `20261102120000` и `20261103120000` создают хранилище и ключ
  идемпотентности.

Нынешняя модель не является очередью push-доставки. Реестр
`push_subscriptions` отдельно хранит FCM-токены web-устройств, связанные с
пользователем, browser ID и server-side JWT-сессией, но не содержит
статусов/попыток внешней доставки и ещё не отправляет push.
Для подробного контракта текущего хранилища см. [модель данных
уведомлений](./notifications-data-model.md).

## Референс из `ek-ls-backend`

В `ek-ls-backend` транспортный слой регистрирует устройства, use-case вызывает
порты, а адаптер `app/adapters/notifications/provider.py` выбирает FCM или
No-op провайдер по настройке `PUSH_PROVIDER`. FCM реализован через
`firebase-admin`: для пачки устройств вызывается `messaging.send_each`, а
ответы провайдера преобразуются в результаты доставки и ошибки отдельных
устройств. Firebase Admin app создается лениво и повторно используется в
процессе. Ошибка `UnregisteredError` отмечается как подтверждённая постоянная
недействительность устройства. `InvalidArgumentError` сам по себе не является
основанием отозвать токен: он также может указывать на некорректный payload.

Доставка запускается Celery-задачей в отдельной очереди `notifications` и
обрабатывает записи событий пачками. Повторные попытки и результат доставки
хранятся в БД. Compose подключает каталог `./secrets` только для чтения к
backend и Celery worker. Детали референсного бизнес-триггера и его payload
относятся к накладным `ek-ls-backend` и не переносятся в этот сервис без
отдельного обоснования.

Для сверки реализации использованы `docs/push-notifications-rules.md`,
`docs/push-notifications-implementation-plan.md`,
`app/routes/notifications_route.py`,
`app/adapters/notifications/provider.py`,
`app/tasks/notifications_tasks.py` и `docker-compose.app.yml`.

## Целевая схема здесь

Push-доставка должна дополнять сохранение уведомления, не подменяя его. Сценарий
создает уведомление и событие доставки в одной транзакции с бизнес-изменением
(либо в отдельной надежной транзакционной границе, согласованной с владельцем
бизнес-сценария). Worker отправляет событие после commit. Сбой Firebase не
откатывает уже сохраненную бизнес-операцию и не удаляет in-app уведомление.

Предлагаемые компоненты:

1. Реестр устройств получателя: внутренний ID, `user_id`, платформа, push token,
   стабильный клиентский `device_id`, версия приложения, `enabled`, время
   последней активности и время отзыва.
2. Запись события доставки: ссылка на in-app уведомление, получатель, стабильный
   ключ дедупликации, payload, статус, количество попыток, время следующей
   попытки, время отправки, ID ответа провайдера и последняя ошибка.
3. Use-case публикации push-события, который сохраняет событие надежно и не
   импортирует Firebase SDK или Celery.
4. Порт push-провайдера и Firebase adapter в `app/adapters`, работающий через
   Firebase Admin SDK. В срезе OK-41 этот компонент реализован как
   `app/use_cases/push_notifications/ports.py` и
   `app/adapters/push_notifications/firebase.py`: он принимает явный список
   токенов, но пока не вызывается web-контуром.
5. Отдельный Python worker и очередь в PostgreSQL; их реализация и способ
   запуска определяются в следующем срезе. Celery и Redis не используются.
6. HTTP API регистрации, просмотра, обновления и отзыва собственных устройств
   в web-слое. Все операции ограничиваются текущим пользователем.

Направление зависимостей следует [архитектуре проекта](../ARCHITECTURE.md):
web -> use-case -> domain/ports; adapters реализуют порты. В частности,
Firebase и детали worker не должны попадать в domain/use-case. Разделяйте внутреннее
сохраненное уведомление и внешний push: push содержит краткий текст и данные
для перехода, а не заменяет историю уведомлений.

### Контракт устройства

Клиент получает push token из Firebase SDK и передает его backend вместе со
стабильным `device_id` и платформой. Backend связывает устройство с текущим
пользователем. При обновлении токена запись устройства обновляется; logout или
отключение push отзывает устройство. Push отправляется только на включенные и
неотозванные устройства текущего получателя. Перед разработкой endpoints нужно
зафиксировать их точные URL и JSON-схемы вместе с клиентом.

Уникальность токена и правила переноса одного `device_id` между пользователями
надо определить в задаче реализации. Референс `ek-ls-backend` перепривязывает
совпавший токен/идентификатор устройства к новому пользователю; применять это
поведение следует только после проверки требований к сессиям и безопасности
клиентов `ok-service-backend`.

### Доставка, повтор и ошибки

- Событие получает стабильный idempotency/dedup key от источника факта; ключ не
  строится из текста уведомления.
- Worker выбирает ожидающие и готовые к повтору записи, ограничивая размер
  пачки.
- Временные ошибки Firebase планируются на повтор с ограниченным backoff и
  пределом попыток.
- Постоянная ошибка токена отзывает или отключает конкретное устройство; она не
  должна бесконечно повторять доставку всего события.
- Успех, частичный успех и ошибка каждого адресата фиксируются отдельно так,
  чтобы повтор не отправлял уже успешно доставленные адресаты повторно.
- Уведомления с одинаковым ключом не создаются повторно. Правило дедупликации
  должно учитывать, что внешний push может быть принят Firebase, а процесс
  завершиться до записи результата: без подтверждения от клиента нельзя
  обещать exactly-once доставку.
- Ошибки и метрики не должны содержать полный push token, JSON service account,
  приватные ключи или другой секрет. Для корреляции используйте ID события и
  устройства.

Firebase payload текущего provider-а минимален: `notification_id`, `title`,
`body` и application-relative `route`. Чувствительные поля, полные профили,
финансовые данные и секреты передавать запрещено. Список первых событий,
получатели и текст уведомления фиксируются в документации соответствующей
бизнес-функции; данный документ не вводит бизнес-триггер.

## Firebase-конфигурация и секреты

Backend использует Firebase Admin SDK с service account конкретного Firebase
project. Service account JSON является секретом. Не помещайте его в репозиторий,
образ, `.env`, логи, Changelog или примеры конфигурации. Храните файл на хосте в
`secrets/`, ограничьте права чтения пользователем Docker runtime и не выдавайте
избыточные права service account.

Compose подключает каталог только worker и только для чтения:

```yaml
  push-worker:
    volumes:
      - ./secrets:/app/secrets:ro
```

В целевую конфигурацию передаются несекретный ID проекта и путь внутри
контейнера, например:

```dotenv
PUSH_PROVIDER=fcm
FCM_PROJECT_ID=<firebase-project-id>
GOOGLE_APPLICATION_CREDENTIALS=/app/secrets/firebase-service-account.json
```

Отправка выполняется только worker, а не HTTP-процессом. Service account передаётся только путём в
`GOOGLE_APPLICATION_CREDENTIALS`; JSON в переменных окружения не поддерживается.
Firebase App переиспользуется в пределах процесса. Для production указывается
путь к credentials-файлу из read-only mount.

Перед запуском требуется:

- задать настройки worker через принятый в проекте механизм `.env`;
- создать каталог `secrets` на хосте и разместить там service account файл;
- исключить `secrets/` из Git и проверить, что секрет не копируется в Docker
  image build context.

`secrets/` уже исключён из `.gitignore` и `.dockerignore`; перед сборкой всё
равно следует проверить build context и CI. Сам service account не добавляется
в репозиторий или Docker image.

Frontend Firebase Web config и VAPID public key нужны браузерному клиенту и не
являются service account credentials. Они настраиваются отдельно на клиенте;
приватные backend credentials туда не передаются.

## Что остается определить до реализации

Бизнес-требования проекта не задают в этом документе:

- какие события `ok-service-backend` должны инициировать push и кто их получатель;
- нужно ли создавать запись in-app для каждого push;
- целевой клиентский контракт и его endpoints;
- предпочтительные гарантии хранения и конкурентного захвата задач worker;
- расписание/способ запуска очереди и пределы retry;
- правила для нескольких активных устройств и очистки устаревших токенов.

Эти решения фиксируются для конкретной функции до реализации ее бизнес-логики.
Не копируйте триггеры назначения курьера из `ek-ls-backend`: они относятся к
другой предметной области.

## Проверки при реализации

Покрыть тестами регистрацию и отзыв устройства, проверку владельца, дедупликацию
событий, успешную и частично успешную отправку, временные/постоянные ошибки,
повтор после сбоя и отсутствие регрессий хранилища in-app уведомлений. Firebase
SDK в unit-тестах подменяется портом/адаптером; интеграционная проверка с Firebase
должна использовать отдельный тестовый проект и credentials из внешнего
тестового секрета. Проверить разрешения mount внутри контейнера, не печатая
содержимое credential-файла.


## Первый срез OK-41: реестр подписок

Реализованы domain, use-case, PostgreSQL-репозиторий и защищённый HTTP-маршрут
регистрации без отправки. `push_subscriptions` хранит UUID записи, пользователя и браузера,
`platform=web`, FCM token, `active`, `created_at`, `updated_at`, `revoked_at`;
время — Unix epoch milliseconds. Уникальны пара пользователь/браузер, а среди
активных записей — браузер и токен. При регистрации повторная пара сохраняет
UUID, токен обновляется, прежние активные записи с тем же браузером или токеном
отзываются в одной транзакции. Отзыв доступен только владельцу и идемпотентен.
При удалении пользователя записи удаляются каскадно. Токен не следует выводить
в ответах и логах. Регистрации сериализуются общей транзакционной advisory lock PostgreSQL;
дополнительно используются блокировки идентификаторов и уникальные индексы; прямые записи в таблицу должны соблюдать те же инварианты.

`PUT /notifications/push/subscription`
с JSON `{"platform":"web","token":"..."}` для регистрации текущего браузера
и `DELETE /notifications/push/subscriptions/{subscription_id}` для отзыва.
Пользователь и auth_session извлекаются из проверенного JWT, browser_id — из
существующей HttpOnly cookie. Отсутствующая/повреждённая cookie даёт `401` и не
изменяет записи. Ответ содержит ID, платформу, active и времена, без токена.

С 20261106120000 новые активные записи дополнительно привязаны к
`auth_session_id`; исторические активные записи при миграции отзываются, так
как их нельзя безопасно связать с конкретной сессией. Login создаёт/сохраняет
browser_id для новой auth-сессии и в одной транзакции отзывает предыдущую
активную подписку браузера. Login одного browser_id сериализован до чтения
прежних сессий. Logout и обнаруженный reuse refresh-токена отзывают подписку по
сохранённой паре `user_id` и `auth_session_id`, а не по cookie браузера.
В первом срезе реальная доставка ещё не выполнялась.

## Вывод legacy Web Push из HTTP-контура

Существовавший namespace `/subscriptions/*` с `pywebpush` временно отключён:
он больше не регистрируется в Flask API и его HTTP-маршруты недоступны. Таблица
`subscriptions`, ORM-модель и исходный код оставлены без миграции, чтобы данные
не удалялись этим срезом. Новый реестр `push_subscriptions` остаётся отдельной
подготовленной основой для Firebase; legacy HTTP API отправки по-прежнему не
возвращается.

## Второй срез OK-41: PostgreSQL очередь доставки

`push_deliveries` — долговечная очередь с одной записью на пару персональный
получатель уведомления–push-подписка. Создание `notifications`,
`notification_recipients` и задач для активных сессий получателей выполняется
одной PostgreSQL-транзакцией. Уникальность пары делает повторное создание
уведомления с тем же idempotency key безопасным; worker не вызывается до commit.

Процесс `python -m app.push_worker` короткой транзакцией выбирает готовые
`pending`/`retry` и просроченные `processing` задачи через `FOR UPDATE SKIP
LOCKED`, назначает lease (`locked_until`, `locked_by`, UUID lease token) и
только затем обращается к Firebase без открытой SQL-транзакции. Подтверждение
результата требует тот же lease token, поэтому старый worker после lease expiry
не может подтвердить либо отозвать устройство; срок проверяется по времени
PostgreSQL после получения блокировки строки. Отзыв недействительного токена
применяется только если токен подписки не изменился после claim. Повтор имеет ограниченный
exponential backoff с jitter; успех — `sent`, `UnregisteredError` — `failed` с
отзывом подписки, остальные диагностируемые ошибки — `retry`, затем `failed`
после лимита. В error-поле сохраняется только код/тип ошибки, не токен и не
credentials.

`PUSH_WORKER_RETRY_MAX_SECONDS` ограничивает итоговую задержку с учётом jitter.
`PUSH_PROVIDER` должен быть явно задан как `noop` или `fcm`; некорректное
значение и отсутствующие обязательные настройки FCM вызывают ошибку конфигурации.

Worker получает по одному заданию непосредственно перед отправкой; параметр
`PUSH_WORKER_BATCH_SIZE` ограничивает число заданий за проход. HTTP timeout
Firebase SDK равен меньшему из 10 секунд и трети lease. Это timeout отдельного
запроса, а не жёсткая граница всего вызова SDK с авторизацией и повторами:
при превышении lease другая попытка может начать отправку параллельно.

Перед Firebase-вызовом worker одним запросом проверяет существование активного,
не удалённого получателя, принадлежность подписки и неотозванной непросроченной
сессии этому пользователю, активность подписки, неизменность токена и сессии
после claim и действующий lease. Неподходящая задача переходит в `failed` без
отзыва подписки и удаления истории. Ошибка БД не считается отказом в допуске:
worker повторяет работу после паузы, а полученный lease восстанавливается после
истечения; исчерпание существующего лимита попыток по-прежнему завершает задачу.
Logout или деактивация до этой проверки предотвращают отправку. Между такой проверкой и внешним
вызовом существует неустранимая гонка: Firebase может принять сообщение, когда
logout или деактивация уже произошли, а также принять его до crash worker до записи `sent`.
Следовательно, очередь обеспечивает at-least-once попытки и не заявляет
exactly-once физическую доставку. Краткий lease, повторная проверка и отзыв при
logout уменьшают окно; клиент должен считать сессию/данные авторитетными и не
раскрывать приватное содержимое только из push payload.

В `docker-compose.app.yaml` добавлен `push-worker` на том же image, с `.env`,
read-only `secrets` и без публикации порта. Для включения задаются
`PUSH_PROVIDER=fcm`, credentials path и параметры `PUSH_WORKER_*`; явно выбранный
provider `noop` не отправляет push, а задания завершатся после retry limit без отзыва
устройства. Перед включением нужно применить Alembic migration
`20261107120000` и убедиться, что worker имеет тот же доступ к PostgreSQL и
read-only credentials mount.

## Dev: deployment и эксплуатация worker

GitHub Actions для ветки `dev` после `alembic upgrade head` и обновления web
запускает управляемый Compose worker с тем же SHA-тегом. Перед запуском pipeline
проверяет FCM, положительные значения настроек и доступность JSON под UID/GID
`1000:1000`; `secrets/` монтируется только для чтения. Параметры
`PUSH_WORKER_BATCH_SIZE`, `PUSH_WORKER_POLL_INTERVAL_SECONDS`,
`PUSH_WORKER_LEASE_SECONDS`, `PUSH_WORKER_MAX_ATTEMPTS`,
`PUSH_WORKER_RETRY_BASE_SECONDS`, `PUSH_WORKER_RETRY_MAX_SECONDS` можно задать
в `.env`, иначе используются значения из `config.py`. Каталог должен быть
доступен для прохода, а файл для чтения пользователю `1000:1000` без выдачи
лишних прав. JSON не должен попадать в Git, образ, CI artifacts или логи.
Pipeline не проверяет права Firebase и не отправляет тестовый push.

Перед **первым** deployment на dev оператору необходимо в каталоге проекта
проверить и штатно остановить именно временный контейнер. Согласуйте остановку
с отключением автоматических запусков до окончания процедуры:

```bash
docker ps --filter 'name=^/ok-service-backend-dev-push-worker-run-' --format '{{.ID}} {{.Names}} {{.Status}}'
# Подставьте ID конкретного контейнера из вывода после проверки имени:
docker stop --time 60 <container_id>
docker ps --filter 'name=^/ok-service-backend-dev-push-worker-run-' --format '{{.ID}} {{.Names}} {{.Status}}'
```

Убедитесь, что список пуст, и только после этого запускайте deployment. Pipeline
сам откажет в запуске, если контейнер с указанным именем ещё работает; он не
удаляет контейнеры. Если временный worker запускался с иным Compose project name,
найдите его по labels и остановите вручную: автоматическая проверка ищет только
указанный dev-префикс. Остановка ожидает завершения текущей операции до таймаута;
при принудительном завершении незаконченная задача вернётся после lease.

Команды ниже выполняются на dev из каталога проекта. Не выводите `.env`, JSON
credentials или полные значения переменных в логи и обращения за поддержкой.

```bash
# Состояние и журнал
docker compose -f docker-compose.app.yaml ps -a push-worker
docker compose -f docker-compose.app.yaml logs --tail=100 -f push-worker

# Проверить именно загруженную приложением конфигурацию без вывода её значений
docker compose -f docker-compose.app.yaml exec -T push-worker python -c 'from config import Config; print("provider=fcm:", (Config.PUSH_PROVIDER or "").strip().lower() == "fcm")'

# Сравнить image ID контейнеров; при штатном деплое они должны совпадать
docker inspect --format '{{.Image}}' "$(docker compose -f docker-compose.app.yaml ps -q web)"
docker inspect --format '{{.Image}}' "$(docker compose -f docker-compose.app.yaml ps -q push-worker)"

# Очередь: агрегаты без токенов и содержимого уведомлений
docker compose -f docker-compose.app.yaml exec -T web python -c 'from sqlalchemy import create_engine, text; from config import Config; e = create_engine(Config.SQLALCHEMY_DATABASE_URI); c = e.connect(); print(c.execute(text("SELECT status, count(*) FROM push_deliveries GROUP BY status ORDER BY status")).fetchall()); c.close(); e.dispose()'

# Перезапуск / временная остановка обработки
docker compose -f docker-compose.app.yaml restart push-worker
docker compose -f docker-compose.app.yaml stop -t 60 push-worker
```

Следующий dev deployment снова запустит остановленный worker. Для диагностики
startup или PostgreSQL проверьте `ps -a` и логи, доступность PostgreSQL из сети
контейнера, миграцию `alembic current` через web и доступ UID к файлу credentials;
не выводите URL БД и секреты. Успешная проверка в течение 10 секунд и статус
`running` не подтверждают последующую работоспособность, авторизацию Firebase
или доставку сообщения. Отслеживайте очередь и результат контролируемой
проверки доставки отдельно.
