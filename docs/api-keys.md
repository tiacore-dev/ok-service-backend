# API-ключи: хранение и аутентификация

## Хранение

- В таблице `api_keys` хранится только SHA-256 хэш ключа в колонке
  `api_key_hashed` (hex, 64 символа, `UNIQUE`, `NOT NULL`). Открытое значение
  ключа в БД не хранится.
- Хэширование: `app.domain.api_keys.hash_api_key` —
  `sha256(utf-8(key)).hexdigest()`.
- Почему SHA-256, а не bcrypt/argon2: ключи генерирует сервис
  (`secrets.token_urlsafe(48)`, ~384 бита энтропии), перебор невозможен,
  поэтому медленная KDF не даёт защиты, но мешает поиску по индексу.
  Детерминированный хэш позволяет найти ключ одним запросом по уникальному
  индексу.

## Выпуск ключа

`POST /api-key/generate` возвращает открытый ключ в поле `token` **один раз**.
Сохраняется только хэш, повторно получить ключ нельзя: `GET /api-key/all` и
`GET /api-key/{api_key_id}/view` не возвращают ни ключ, ни хэш. Потерянный
ключ нужно удалить и выпустить заново.

## Аутентификация

Заголовок `API-Key` хэшируется и ищется по `api_key_hashed`. Дальнейшие
проверки не изменились: срок действия (`expires_at`), разрешение маршрута через
`key_permission_type_relations`, работа от имени администратора. Удалённый
ключ, неверный ключ и сам хэш вместо ключа отклоняются с `403`.

## Миграция `20261108120000`

- Добавляет `api_key_hashed`, заполняет его в PostgreSQL выражением
  `encode(sha256(convert_to(token, 'UTF8')), 'hex')` и удаляет колонку `token`.
  Открытые ключи не проходят через Python, логи и параметры запросов.
- Существующие ключи продолжают работать без перевыпуска: SQL-хэш совпадает с
  `hash_api_key`.
- Требуется PostgreSQL 11+ (встроенная функция `sha256`).
- Downgrade запрещён: открытые ключи восстановить нельзя. Откат возможен только
  из резервной копии, снятой до миграции.

### Порядок деплоя

Обе части (хэш и удаление `token`) выходят одним релизом. CI выполняет
`alembic upgrade head` до перезапуска `web`, поэтому в промежутке между
миграцией и рестартом старая версия приложения не сможет аутентифицировать
API-ключи (её модель обращается к удалённой колонке `token`). JWT-запросы не
затрагиваются. После перезапуска `web` все ключи, включая старые, работают.
Перед деплоем в production рекомендуется снять резервную копию `api_keys`.
