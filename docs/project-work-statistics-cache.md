# Redis-кэш статистики работ проекта

Документ фиксирует согласованное целевое поведение до переноса расчёта
статистики из запросов в Redis. На этапе добавления инфраструктуры API и
текущий расчёт не изменяются.

## Область агрегации

Статистика рассчитывается отдельно для каждого `project_id` и группируется по
`work_id`. Одинаковые `work_id` из разных проектов никогда не объединяются.
Это сохраняет действующий контракт `GET /projects/{project_id}/get-stat`.

Для пары `(project_id, work_id)` сохраняются:

1. `project_work_quantity` — сумма `ProjectWorks.quantity` всех строк
   спецификации проекта с этим `work_id`.
2. `shift_report_details_quantity` — сумма `ShiftReportDetails.quantity` с этим
   `work_id` только из сменных отчётов данного проекта, у которых `signed = true`.
3. `acceptance_status` не хранится отдельно: он детерминированно выводится при
   формировании ответа: `not_checked` при факте `0`, `partial` при факте больше
   `0` и меньше плана, иначе `accepted`.

Таким образом, показатели относятся к работе в спецификации проекта, а не к
одной строке `project_works` (`project_work_id`).

## Хранение

Целевой ключ Redis: `project-work-stats:{project_id}`. Значения для `work_id`
будут записываться как агрегаты одной спецификации проекта. TTL намеренно не
назначается: актуальность обеспечивается пересчётом после изменения исходных
данных, а не временем жизни ключа.

Формат записи и сервис чтения будут добавлены следующим этапом. Для уже
существующих проектов потребуется отдельный первоначальный пересчёт; до него
пустой Redis не может считаться источником корректной статистики.

## План пересчёта

После внедрения кэша пересчёт спецификации будет запускаться после успешной
фиксации транзакции при:

- создании, изменении и удалении смены, включая изменение `signed` и `project`;
- создании, изменении и удалении детали смены, включая изменение `work`,
  `project_work` и `shift_report`;
- создании, изменении и удалении строки `project_works`, включая изменение
  `work`, `quantity` и `project`.

Если запись переносится между проектами или работами, пересчитываются и старые,
и новые затронутые агрегаты. Это предотвращает устаревшие значения.

## Использование API

Следующим этапом `project_works/all` будет всегда возвращать
`project_work_quantity`, `shift_report_details_quantity` и
`acceptance_status`. В `GET /shift_report_details/all` и
`POST /shift_report_details/all-by-reports` сохранится параметр `with_stat`;
при `true` данные будут читаться из подготовленного Redis-агрегата, а не
пересчитываться для каждой строки ответа.

## Конфигурация и запуск

В `requirements.txt` используется `redis==5.2.1`. Flask создаёт клиент в
`app.extensions["redis"]` через `Redis.from_url(..., decode_responses=True)`.
Создание клиента не вызывает `PING` и не открывает соединение: сеть будет
использована только при первой Redis-команде.

- `REDIS_URL` — URL Redis приложения. Для локального запуска по умолчанию:
  `redis://localhost:6379/0`.
- `TEST_REDIS_URL` — URL для тестов; по умолчанию:
  `redis://localhost:6379/1`.
- В контейнерной сети из `docker-compose.infrastructure.yaml` следует задать
  `REDIS_URL=redis://ok-service-backend-redis:6379/0`.

Инфраструктурный сервис запускается командой:

```bash
docker compose -f docker-compose.infrastructure.yaml up -d redis
```

Файл compose использует внешнюю сеть `ok_network`; она должна существовать до
запуска.
