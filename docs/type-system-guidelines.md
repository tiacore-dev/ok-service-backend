# Правила типизации

Этот документ фиксирует практические правила типизации для сервиса. Цель не в том, чтобы убрать все `cast`, а в том, чтобы ограничить их одной границей и сделать ошибки типов предсказуемыми.

## Базовый принцип

Типы должны подтверждать границы слоёв:

- `domain` и `use-case` типизируются как обычный Python-код без зависимости от Flask.
- `adapters` типизируются вокруг ORM, внешних клиентов и мапперов.
- `web` обязан нормализовать `request`-данные до вызова `schema.load()` и use-case.

## Общие helper-ы

Для web-слоя используются общие helper-ы из `app/web/_typing.py`:

- `require_mapping(...)` и `to_plain_dict(...)` для нормализации `request`-payload;
- `required_uuid(...)` и `optional_uuid(...)` для UUID-конверсий;
- `get_optional_str(...)`, `get_optional_int(...)`, `get_optional_bool(...)` для безопасного доступа к optional полям.

Если новый namespace начинает повторять локальные `_optional_*` или `_require_*` функции, сначала попробуй вынести их на этот общий уровень.

## Общие helper-ы adapters

Для adapter-слоя используются общие helper-ы из `app/adapters/_typing.py`:

- `to_uuid(...)` и `require_uuid(...)` для UUID-конверсий;
- `normalize_result(...)` для перевода ORM-объектов и DTO в dict;
- если mapper или repository начинает повторять `_to_uuid`, `_require_uuid` или `_normalize_result`, сначала вынеси их в общий adapters helper.

## Правила для web-слоя

1. Не передавать `request.json` напрямую в `schema.load()`.
2. Сначала получить payload через `request.get_json(silent=True)`.
3. Если payload может отсутствовать, проверить это явно и вернуть `400`.
4. Для query string использовать `request.args.to_dict()`, а не работать с `ImmutableMultiDict` напрямую.
5. Не индексировать `TypedDict` по необязательным ключам.
6. Для необязательных значений использовать helper-функции вида `_optional_uuid(...)`, `_optional_int(...)`, `_optional_bool(...)`.
7. `cast(...)` использовать только после runtime-проверки, когда тип уже подтвержден, но проверка не видна анализатору.

## Правила для DTO

1. DTO должны отражать форму данных, которая реально нужна use-case.
2. Обязательные поля делать обязательными в `TypedDict` или dataclass.
3. Необязательные поля не индексировать напрямую.
4. Если поле участвует только в одном сценарии, не тащить его в общий DTO.

## Правила для adapter-мапперов

1. Любой `None`, который недопустим по контракту сущности, надо отбрасывать явно.
2. Mapper должен либо вернуть корректную сущность, либо бросить понятную ошибку.
3. Не оставлять `UUID | None` в аргументах доменной сущности, если по контракту там обязателен `UUID`.
4. Конвертации строковых идентификаторов делать в одном месте, а не по всему коду.

## Правила для use-case

1. Use-case не должен знать про `request`, `TypedDict` транспорта и `ImmutableMultiDict`.
2. Use-case принимает уже нормализованные значения.
3. Не делать в use-case транспортных `cast`, если это можно решить на web-границе.

## Практическая схема

Рекомендуемый порядок для веб-слоя:

1. Взять `payload = request.get_json(silent=True)`.
2. Проверить `payload is not None`.
3. Нормализовать `payload` в `dict`.
4. Передать в `schema.load(...)`.
5. Сконвертировать значения в UUID и другие доменные типы через helper-функции.
6. Только после этого создать command DTO.

Это уменьшает количество ложных предупреждений Pylance и делает runtime-поведение явным.
