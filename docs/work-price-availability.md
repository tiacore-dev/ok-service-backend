# Цены работ и доступность работ для категории исполнителя

## Допустимые значения `work_prices.price`

| Значение | Смысл |
| --- | --- |
| `> 0` | Оплата за единицу работы. |
| `0` | Работа неоплачиваемая, но доступна. |
| `-1` | Работа **недоступна** для категории (`work_prices.category`). |

Остальные отрицательные значения (`< -1` и между `-1` и `0`) запрещены.

`-1` — это бизнес-маркер, а не сумма. Он никогда не участвует в расчёте
начислений и не может дать отрицательную оплату или удержание.

Правило проверяется:

- в `WorkPriceCreateSchema` / `WorkPriceEditSchema` (`400`);
- в use-case `CreateWorkPriceUseCase` / `UpdateWorkPriceUseCase`
  (`validate_work_price_value` из `app/domain/work_prices/policies.py`);
- в БД: `CHECK (price >= 0 OR price = -1)`, ограничение
  `check_work_prices_price_values`.

### Миграция `20261111120000`

Ограничение добавлено как `NOT VALID`: PostgreSQL проверяет каждую новую
вставку и изменение строки, но не перепроверяет и не меняет существующие
записи. Старые строки читаются как раньше. После проверки исторических
данных ограничение можно провалидировать вручную:

```sql
ALTER TABLE work_prices VALIDATE CONSTRAINT check_work_prices_price_values;
```

Миграция также добавляет индекс `ix_work_prices_work_category` по
`(work, category)` — по этим колонкам ищется цена при расчёте начислений и
при проверке доступности.

## Запрет добавления недоступной работы в смену

Работа недоступна для смены, если у неё есть неудалённая (`deleted = false`)
цена `-1` для категории **исполнителя смены** (`shift_reports.user` →
`users.category`). Категория и роль пользователя, отправившего запрос, не
учитываются.

Проверка выполняется при добавлении, замене или переносе работы, а также при
изменении количества в детали с работой, недоступной для категории исполнителя:

| Операция | Что проверяется |
| --- | --- |
| `POST /shift_report_details/add` | работа детали |
| `POST /shift_report_details/add/many` | все работы пакета до первой записи |
| `PATCH /shift_report_details/{id}/edit` | итоговая `work` (новая или текущая) для исполнителя итоговой смены (`shift_report` из запроса или текущая), если меняется `work`, `shift_report` или `quantity` |
| `POST /shift_reports/add` | работы из `details` для `user` смены |
| `POST /shift_reports/add-bulk` | работы из `details` для каждого `user_ids` |

При нарушении ничего не сохраняется (в пакетных операциях — ни одна запись),
ответ `409`:

```json
{
  "msg": "Работа недоступна для категории исполнителя",
  "code": "WORK_UNAVAILABLE_FOR_PERFORMER_CATEGORY",
  "work_ids": ["<uuid>"]
}
```

`work_ids` содержит все недоступные работы запроса.

### Существующие записи

- Сохранённые детали смен и их начисления не меняются.
- Чтение (`view`, `all`, `all-by-reports`) работает для любых записей.
- Изменение только `project_work` или повторная отправка тех же `work`,
  `shift_report` и `quantity` у исторической детали разрешены.
- Изменение `quantity` у детали, чья работа стоит `-1` для категории
  исполнителя, отклоняется с тем же `409`: `-1` не может дать сумму за новое
  количество, а сохранённое `summ` перестало бы ему соответствовать. Это же
  правило дублируется в `ShiftReportsDetailsManager.update_shift_report_details`
  (транзакция откатывается).
- Если цена работы для категории исполнителя равна `-1`, пересчёт по условиям
  смены (изменение `night_shift` / `extreme_conditions`) оставляет сохранённое
  `summ` без изменений: `-1` не используется в расчёте.
- Цены `0` и положительные рассчитываются как раньше.

## API выбора работ для смены

`GET /works/all` и `GET /project_works/all` принимают необязательный параметр
`shift_report` (UUID смены). Если он передан, у каждого элемента появляются поля:

| Поле | Тип | Описание |
| --- | --- | --- |
| `available` | `bool` | Можно ли добавить работу в эту смену. |
| `unavailable_reason` | `string \| null` | Причина недоступности, `null` если доступна. |

Причина для цены `-1`: `"Работа недоступна для категории исполнителя"`.
Несуществующая смена — `404`.

Без `shift_report`:

- `GET /project_works/all` — ответ не меняется, полей нет;
- `GET /works/all` — поля присутствуют со значением `null` (ответ
  сериализуется через `marshal_with`).

Фронтенд может блокировать недоступные работы и показывать
`unavailable_reason`, но запрет в любом случае применяется на backend.
