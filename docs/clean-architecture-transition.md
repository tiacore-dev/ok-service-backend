# План перехода на clean architecture

Этот документ описывает, как перевести сервис с текущей структуры на слои `domain / use-case / adapters / web` без большого одномоментного переписывания.

## Цель

Нужно убрать из роутеров:

- бизнес-правила;
- проверки ownership;
- длинные ветки `if` со сценарной логикой;
- прямую работу с менеджерами, когда она нужна только как часть use-case;
- часть маппинга ошибок и ответа.

При этом API и пользовательское поведение должны оставаться совместимыми, пока миграция не завершена.

## Основной принцип

Переезд делаем не по слоям целиком, а по вертикальным срезам:

1. выбираем одну фичу;
2. выделяем её доменную модель;
3. выносим use-case;
4. подключаем адаптеры;
5. упрощаем web-слой;
6. только потом трогаем следующую фичу.

Такой подход безопаснее, чем массово рефакторить все роуты сразу.

## Этапы миграции

### Этап 0. Зафиксировать договоренности

Результат этапа:

- есть этот документ;
- есть `ARCHITECTURE.md`;
- понятны правила зависимостей;
- понятен порядок переезда;
- команда не импровизирует архитектуру в каждом роуте заново.

### Этап 1. Ввести целевые каталоги

Нужно создать и начать наполнять:

- `app/domain/`
- `app/use_cases/`
- `app/adapters/`
- `app/web/`

На этом этапе допустимо:

- копировать только минимум кода;
- оставлять старые маршруты как shim;
- переиспользовать существующие менеджеры как адаптеры.

### Первый срез: `leaves`

Для первого практического перевода лучше взять `leaves`, потому что в этом namespace уже смешаны:

- аутентификация и authorization;
- проверка конфликтов отпусков и смен;
- CRUD;
- работа с `AbsenceReason`;
- преобразование входа и ответа;
- прямые обращения к `LeavesManager` из web-слоя.

Текущая логика в [`app/routes/namespaces/leave_ns.py`](../app/routes/namespaces/leave_ns.py) должна быть разложена так:

- `domain`
  - `Leave` как сущность;
  - `AbsenceReason` как доменный enum;
  - доменные ошибки вроде `LeaveConflictError`, `LeaveNotFoundError`, `LeaveValidationError`.
- `use-case`
  - `CreateLeave`;
  - `GetLeave`;
  - `UpdateLeave`;
  - `SoftDeleteLeave`;
  - `HardDeleteLeave`;
  - `ListLeaves`;
  - `ListAbsenceReasons`.
- `adapters`
  - `LeavesRepository` как порт-реализация поверх ORM;
  - чтение и запись через SQLAlchemy;
  - проверка конфликтов как инфраструктурный доступ к данным;
  - маппинг ORM -> domain DTO.
- `web`
  - Flask-RESTX resource для `/leaves`;
  - парсинг `request.json` и `request.args`;
  - вызов use-case;
  - маппинг доменных ошибок в HTTP.

Целевая структура файлов для этого среза может выглядеть так:

```text
app/
  domain/
    leaves/
      entities.py
      errors.py
      policies.py
  use_cases/
    leaves/
      create_leave.py
      get_leave.py
      update_leave.py
      delete_leave.py
      list_leaves.py
      list_absence_reasons.py
      ports.py
      dto.py
  adapters/
    leaves/
      sqlalchemy_repository.py
      mappers.py
  web/
    leaves/
      routes.py
      schemas.py
      responses.py
```

Если использовать этот срез как шаблон, то следующие namespace можно переводить по тому же принципу, не изобретая новый стиль для каждого файла.

### Этап 2. Перенести бизнес-правила из web в use-case

Что переносим первым:

- проверки прав, завязанные на бизнес-сценарий;
- правила ownership;
- конфликты состояний;
- сценарии "можно/нельзя" по сущности;
- составные операции, которые затрагивают несколько репозиториев.

Что оставляем в web:

- чтение `request`;
- базовую валидацию формата;
- вызов use-case;
- маппинг исключений в HTTP.

### Этап 3. Вынести доменные модели

Нужно отделить:

- сущности и value objects от ORM-моделей;
- бизнесовые статусы и переходы от транспортных enum/строк;
- внутренние ошибки от HTTP-ошибок.

Если доменная модель пока слишком дорогая для полного выделения, можно начать с DTO и доменных ошибок, но не тащить ORM дальше в use-case.

### Этап 4. Оформить порты

Use-case не должен знать, как именно читаются и пишутся данные.

Для этого нужны порты:

- repository port;
- unit of work / transaction port, если сценарий требует;
- service port для внешних интеграций;
- permission/policy port, если решение зависит от внешнего источника.

Текущие менеджеры можно адаптировать под эти порты без переписывания всего слоя сразу.

### Этап 5. Перевести менеджеры в adapters

Задача менеджеров на этом этапе:

- работать с ORM и сессиями;
- возвращать данные в форме, удобной use-case;
- не решать, какой HTTP ответ отдавать;
- не держать предметные правила, если они уже переехали в use-case.

Если какой-то менеджер сейчас содержит много сценарной логики, его лучше разобрать на:

- repo adapter;
- domain service/use-case helper;
- mapper.

### Этап 6. Упростить web

После переноса сценария web-слой должен превратиться в тонкий transport layer.

Что должно остаться:

- маршруты;
- авторизация на входе;
- marshalling/serialization;
- error mapping;
- composition root.

Что должно исчезнуть:

- ручные проверки прав по нескольким сущностям;
- многоступенчатые сценарии внутри `Resource`;
- вызовы нескольких менеджеров для реализации одного бизнес-процесса;
- SQL/ORM-детали в обработчике запроса.

### Этап 7. Убрать legacy-bridge

Когда все срезы переведены:

- старые маршруты и временные шины больше не нужны;
- бизнес-логика из `app/routes/*` удаляется;
- `app/web` становится единственным транспортным слоем;
- composition root регистрирует web-слой напрямую.

## Приоритет миграции

Идти лучше по следующему порядку:

1. самые "шумные" роуты с большим количеством логики;
2. сценарии с правами и ownership;
3. сценарии с несколькими сущностями и конфликтами;
4. CRUD, который проще всего вынести в use-case и adapter;
5. маршруты, где логика почти отсутствует, чтобы закрепить новый шаблон.

## Что переносить особенно рано

Раньше всего стоит убирать:

- проверку прав в роутере, если она относится к сценарию, а не к факту аутентификации;
- создание нескольких менеджеров в одном handler;
- ветвления, которые влияют на бизнес-результат;
- прямую работу с ORM-моделью в ответе.

## Что оставить временно

На переходный период допустимо оставить:

- старые decorators для грубой auth-проверки;
- менеджеры как адаптеры;
- совместимые shims в старых местах импорта;
- существующие транспортные схемы, если они не ломают границы слоев.

Недопустимо только одно: считать временный мост новым целевым архитектурным состоянием.

## Риски и как их снижать

### Риск: слишком большой рефакторинг за раз

Снижение:

- переезд только одним вертикальным срезом;
- частые маленькие изменения;
- обязательная проверка, что старый контракт не сломан.

### Риск: логика расползется между слоями

Снижение:

- до начала работы писать, где находится правило;
- в web держать только transport concerns;
- в use-case держать сценарий целиком.

### Риск: менеджеры останутся "бог-объектами"

Снижение:

- разбирать их на порты и адаптеры;
- не добавлять туда новую бизнес-логику;
- по мере миграции выносить сценарные проверки в use-case.

## Критерии завершения миграции для одной фичи

Фича считается переведенной, если:

- endpoint вызывает use-case, а не содержит сценарий сам;
- use-case работает через порт/адаптер;
- доменные правила покрыты тестами;
- ORM не протекает в web-ответ;
- права и ownership проверяются не в handler-спагетти;
- старый код не нужен для выполнения этого сценария.
