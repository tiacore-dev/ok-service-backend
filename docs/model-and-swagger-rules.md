# Правила построения моделей

Этот документ фиксирует, как строить транспортные модели Flask-RESTx и marshmallow-схемы так, чтобы они не ломали контракт API и не смешивали разные сценарии одного ресурса.

## Базовый принцип

Модель описывает не "сущность вообще", а конкретную форму данных на конкретной границе:

- `create`-модель для `POST`;
- `edit`-модель для `PATCH` или `PUT`;
- `response`-модель для ответа;
- `list`/`all`-модель для коллекции;
- `filter`-parser или `filter`-schema для query string.

Одна модель не должна использоваться сразу для создания и редактирования, если набор обязательных и необязательных полей отличается.

## Правила для create/edit

1. Для `POST` и `PATCH` должны существовать отдельные схемы или хотя бы отдельные модели, если optional-поля отличаются.
2. Если `PATCH` принимает частичный payload, edit-модель обязана отражать это явно.
3. Если поле можно очищать через `null`, edit-схема должна это разрешать.
4. Если поле нельзя очищать, это должно быть видно из схемы и из use-case, а не из случайного поведения marshmallow.
5. `PATCH` нельзя вешать на `create`-модель по умолчанию.

## Правила для response

1. Response-модель должна описывать фактический JSON ответа, а не ORM-объект.
2. Если ответ содержит вложенную сущность, nested-модель должна быть определена отдельно и переиспользоваться.
3. Поля ответа должны быть приведены к JSON-форме на границе web-слоя, а не "как получится" из ORM.

## Правила для list/filter

1. Для `GET /all` и похожих ручек использовать отдельную filter-схему или parser.
2. У filter-схем должны быть безопасные defaults.
3. `limit` должен иметь явный верхний дефолт, если endpoint потенциально может вернуть много строк.
4. Поля filter-схемы должны совпадать с тем, что реально принимает use-case.

## Правила генерации моделей

1. Для schema-to-model конверсии использовать `generate_swagger_model(...)`, если структура совпадает с marshmallow-схемой.
2. Если swagger-контракт отличается от schema, модель описывать явно через `Model(...)`.
3. Не смешивать авторегенерацию и ручную правку в одном и том же контракте без причины.
4. Если добавляется новая edit-модель, она должна быть зарегистрирована в namespace отдельно от create-модели.

## Практические ограничения

1. `request.json` не должен попадать напрямую в модель или schema без нормализации.
2. Если endpoint принимает частичный payload, не пытаться "додумать" недостающие поля в транспортном слое.
3. Если нужен отдельный semantic, например `summ`, `deleted`, `signed` или `project_work`, он должен быть отражён в edit-модели и в use-case-команде.
4. Модель не должна решать бизнес-логику.

## Проверка перед мержем

Перед изменением модели нужно проверить:

- что create/edit модели не перепутаны;
- что типы полей совпадают с текущим payload;
- что response-model не потеряла вложенные поля;
- что filter-параметры не сломали текущие тесты и swagger-контракт.
