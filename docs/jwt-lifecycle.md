# Серверный жизненный цикл JWT

`POST /auth/login` создаёт серверную запись `auth_sessions` и начальную запись
`refresh_tokens` до возврата токенов. Raw JWT в БД и логах не сохраняются.
Access и refresh JWT содержат стандартные `jti`, `iat`, `exp` (Unix seconds) и
дополнительный claim `session_id` (UUID серверной сессии).

`POST /auth/refresh` принимает только действительный refresh JWT с `session_id`.
Операция блокирует сессию, затем текущий refresh-token, помечает его
использованным, записывает новый JTI и возвращает новую access/refresh пару
только после commit. Повторное применение уже использованного токена отзывает
всю сессию и все её refresh-токены в той же транзакции.

Срок серверной сессии скользящий, а не абсолютный: при успешной rotation он
продлевается до срока действия нового refresh JWT, но никогда не сокращается.
Пользователь, который обновляет токены до истечения текущего refresh JWT, не
должен быть принудительно разлогинен только из-за времени первоначального
login.

`POST /auth/logout` требует access JWT в заголовке `Authorization: Bearer` и
не принимает `user_id` или `session_id` в JSON. Он атомарно отзывает только
текущую серверную сессию и все её refresh-токены. Access JWT этой сессии
перестаёт проходить обычный callback. Успех — `204` без тела. Повтор того же
запроса обычно возвращает `401`, поскольку JWT уже отозван; это не является
ошибкой идемпотентности.

Logout в той же транзакции отзывает активную push-подписку, связанную с
пользователем и текущей server-side auth-сессией. Для этого не используется
cookie `browser_id`: отсутствующая, очищенная или повреждённая cookie не может
оставить подписку активной. Cookie не удаляется, так как отдельно используется
для аудита смен и комментариев.

`PUT /notifications/push/subscription` принимает JSON
`{"platform":"web","token":"..."}` и access JWT. Подписка привязывается
к server-side auth-сессии и browser_id; отозванный JWT или несовпадающая cookie
получают `401`. При входе любого пользователя на браузере прежняя активная
push-подписка этого браузера отзывается после успешного создания новой сессии.
Предыдущие auth-сессии того же browser_id также отзываются, поэтому JWT
пользователя A не может зарегистрировать подписку вновь после входа B.
Одновременные login одного browser_id сериализуются отдельной транзакционной
advisory lock до поиска прежних сессий, поэтому активной остаётся только одна
такая сессия.
Frontend должен повторно синхронизировать Firebase subscription после login.

Для каждого JWT-запроса сервер проверяет существование и активность сессии и
пользователя. Access JWT не несёт полномочия как источник истины: role checks
используют актуального пользователя, загруженного из БД. Ошибка БД приводит к
отказу авторизации с `503 Authentication unavailable`; это не означает, что
JWT недействителен. API-key ветка `api_key_or_jwt_required` не использует JWT
callbacks и сохраняет свой прежний permission flow.

## Миграция клиентов

Это breaking change для уже выданных JWT: токены без `session_id` больше не
принимаются. После rollout frontend должен считать сохранённые access и refresh
JWT недействительными, очистить их и выполнить login. На refresh необходимо
атомарно заменить обе сохранённые строки токенов; при `401` удалить их и
перенаправить пользователя на login. Нельзя повторять один и тот же refresh
JWT параллельно: подтверждённый reuse отзывает всю сессию. При `503`
сохранённые токены удалять нельзя: клиент должен повторить запрос с обычной
retry-политикой.

## Контракт для frontend

Для logout отправляйте `POST /auth/logout` с access JWT и без тела. После
подтверждённого `204` удалите локальные access/refresh токены, отзовите Firebase
Web Push subscription и синхронизируйте её с backend при следующем login.
При `401` локальные токены также считаются непригодными; при `503` или сетевой
ошибке серверный logout не подтверждён — клиент может удалить локальные токены
по собственной политике, но должен считать серверную сессию потенциально
активной и повторить запрос после восстановления сети. Не повторяйте logout
тем же JWT как ожидание `204`: после первого успеха ожидаем `401`.
