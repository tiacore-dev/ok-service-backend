# Серверный жизненный цикл JWT

`POST /auth/login` создаёт серверную запись `auth_sessions` и начальную запись
`refresh_tokens` до возврата токенов. Raw JWT в БД и логах не сохраняются.
Access и refresh JWT содержат стандартные `jti`, `iat`, `exp` (Unix seconds) и
дополнительный claim `session_id` (UUID серверной сессии).

`POST /auth/refresh` принимает только действительный refresh JWT с `session_id`.
Операция блокирует сессию, затем текущий refresh-token, помечает его
использованным, записывает новый JTI и возвращает новую access/refresh пару
только после commit. Повторное применение уже использованного токена отзывает
всю сессию и все её refresh-токены в той же транзакции.

Срок серверной сессии скользящий, а не абсолютный: при успешной rotation он
продлевается до срока действия нового refresh JWT, но никогда не сокращается.
Пользователь, который обновляет токены до истечения текущего refresh JWT, не
должен быть принудительно разлогинен только из-за времени первоначального
login.

Для каждого JWT-запроса сервер проверяет существование и активность сессии и
пользователя. Access JWT не несёт полномочия как источник истины: role checks
используют актуального пользователя, загруженного из БД. Ошибка БД приводит к
отказу авторизации с `503 Authentication unavailable`; это не означает, что
JWT недействителен. API-key ветка `api_key_or_jwt_required` не использует JWT
callbacks и сохраняет свой прежний permission flow.

## Миграция клиентов

Это breaking change для уже выданных JWT: токены без `session_id` больше не
принимаются. После rollout frontend должен считать сохранённые access и refresh
JWT недействительными, очистить их и выполнить login. На refresh необходимо
атомарно заменить обе сохранённые строки токенов; при `401` удалить их и
перенаправить пользователя на login. Нельзя повторять один и тот же refresh
JWT параллельно: подтверждённый reuse отзывает всю сессию. При `503`
сохранённые токены удалять нельзя: клиент должен повторить запрос с обычной
retry-политикой.
