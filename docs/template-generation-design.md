# Генерация документов и справочник параметров шаблонов

## Статус и основание

Зафиксировано 19.10.2026 по предоставленному пользователем описанию механизма
EK LS и template-service. Это основа следующего этапа разработки OK Service.
Описание другого проекта рассматривается как референс; его код и работающий
HTTP-контракт в рамках этой фиксации повторно не проверялись.

Документ разделяет текущее состояние, целевой механизм и вопросы до реализации.
Он не означает, что перечисленные ниже возможности уже доступны в API.
Действующий CRUD описан в [templates.md](./templates.md).

## Разделение ответственности

Backend OK Service хранит метаданные шаблонов, управляет исходными файлами в S3,
описывает доступные параметры, проверяет права на операцию и исходные данные,
собирает `document_data` и управляет выдачей или сохранением результата.

template-service получает ссылку на исходный DOCX/XLSX, подставляет переданные
данные и возвращает готовый DOCX/XLSX/PDF. Он не определяет бизнес-структуру
данных OK Service и не заменяет проверки доступа вызывающего backend.

Справочник параметров формируется в OK Service: только вызывающий сервис знает,
какие данные действительно передаются рендереру для каждого типа документа.

## Текущее состояние OK Service

Реализованы хранение метаданных и файлов, CRUD, скачивание и справочник типов
`GET /templates/types/all`. Типы: `work_types`, `shift_report`,
`shift_report_list`, `payroll`, `object_report`; значения английские,
labels русские. Метаданные включают `output_file_name`, `is_pdf`,
`is_horizontal`, `is_default`.

Существующий `POST /templates/generate` принимает `url` или `file_name`,
`name`, `is_pdf` и произвольный `document_data` от клиента. Он не выбирает
сохранённый шаблон, не собирает данные из бизнес-сущностей, не формирует
справочник параметров и не сохраняет результат в attachments.

Текущий HTTP-адаптер отправляет `requests.post` на точный адрес из
`TEMPLATE_SERVICE_URL`; путь `/api/docs/generate` автоматически не добавляется.
В нём нет передачи `x-api-key`, явного timeout и `is_horizontal`.
Адаптер возвращает только байты, а web-слой задаёт имя `output.docx` и MIME DOCX.
Это отличается от референса ниже и требует отдельного изменения интеграции.

Проверенные участки текущего кода:

- `app/web/template_generation/routes.py` — HTTP API;
- `app/schemas/template_schemas.py` — входная схема;
- `app/use_cases/template_generation/` — команда и сценарий;
- `app/adapters/template_generation/http_client.py` — HTTP-адаптер;
- `config.py` — текущая настройка `TEMPLATE_SERVICE_URL`.

## Целевой поток генерации

1. Backend проверяет право на генерацию и доступ к исходной сущности или выборке.
2. Выбирает сохранённый шаблон и проверяет соответствие типу документа.
3. Загружает необходимые бизнес-данные и формирует отдельный DTO для печати.
4. Сериализует DTO в JSON-совместимый `document_data`. UUID, даты и Decimal
   преобразуются по явно описанному контракту конкретного документа.
5. Формирует presigned URL исходного файла в S3, доступный из template-service.
6. Вызывает template-service через HTTP-порт и адаптер.
7. Получает байты результата, Content-Type и Content-Disposition.
8. Выдаёт файл пользователю; если сценарий предусматривает сохранение,
   сохраняет результат через механизм attachments с его правилами доступа.

Метаданные и исходный файл остаются в OK Service/S3. Генерация не должна
перезаписывать исходный файл шаблона.

Для PDF-настроек берём за основу правило референса:

```python
effective_is_pdf = template.is_pdf if requested_is_pdf is None else requested_is_pdf
```

Явное `false` сохраняется. `is_horizontal` берётся из выбранного шаблона.
Применение `output_file_name`, выбор дефолтного шаблона и поведение при его
отсутствии требуют определения до реализации соответствующего сценария.

## HTTP-контракт template-service из референса

В предоставленном описании backend использует настройки:

```text
TEMPLATE_SERVICE_URL=http://template-service:8000
TEMPLATE_SERVICE_API_KEY=...
```

Запрос:

```text
POST {TEMPLATE_SERVICE_URL}/api/docs/generate
Content-Type: application/json
x-api-key: {TEMPLATE_SERVICE_API_KEY}
```

Пример payload, иллюстрирующий транспорт; поля `document` и `details`
не являются согласованной моделью данных OK Service:

```json
{
  "url": "https://storage.example.com/templates/document.xlsx?signature=...",
  "document_data": {
    "document": {"number": "ДОК-001"},
    "details": [{"name": "Пример позиции", "amount": "1500.00"}]
  },
  "name": "Документ ДОК-001",
  "is_pdf": true,
  "is_horizontal": false
}
```

| Поле | Значение в референсе |
| --- | --- |
| `url` | Presigned URL исходного файла, доступный из template-service |
| `document_data` | Объект данных, структуру которого задаёт вызывающий backend |
| `name` | Имя результата без расширения |
| `is_pdf` | Конвертация в PDF либо сохранение Office-формата |
| `is_horizontal` | Альбомная ориентация при PDF-конвертации |

Референс также допускает `file_name` вместо `url`, но интеграция EK LS использует
`url`. Успешный ответ — HTTP 200 с байтами и заголовками файла.
В EK LS используется один `httpx.AsyncClient` на процесс с timeout 30 секунд,
созданием в lifespan и закрытием при shutdown. Это особенность реализации
другого проекта: в OK Service Flask, поэтому способ управления HTTP-клиентом
нужно выбрать в рамках текущей архитектуры, без прямого переноса FastAPI lifespan.

Обработка ошибок в предоставленном описании EK LS:

| Ситуация | Поведение референса |
| --- | --- |
| Нет URL или API-ключа в настройках | HTTP 400 |
| Транспортная ошибка | HTTP 500 с общим сообщением |
| Ответ сервиса отличается от 200 | Сохранение HTTP-статуса, общее сообщение |
| Неверный API-ключ | HTTP 401 |
| Шаблон отклонён рендерером | HTTP 400 |

Эта таблица описывает другой проект. Для OK Service требуется согласовать
маппинг ошибок и совместимость существующего `/templates/generate`;
он сейчас отображает ошибки адаптера в HTTP 500.

## Справочник параметров

Основа будущего контракта OK Service:

```text
GET /templates/parameters?template_type=shift_report
```

Это проектируемый маршрут, сейчас он не реализован. В референсе используется
`GET /api/templates/parameters?entity=act`; в OK Service ключ типа называется
`template_type` и соответствует собственному enum. Справочник описывает тип
документа, а не конкретный загруженный файл или идентификатор сущности.

Форма ответа:

```json
{
  "template_type": "shift_report",
  "parameters": [],
  "schema": {"type": "object", "properties": {}}
}
```

Пустые структуры выше показывают только форму ответа. При реализации они
должны заполняться из утверждённой модели данных типа документа.

Правила справочника из референса:

- `parameters` содержит пути объектов, массивов и вложенных полей.
- Элемент массива обозначается `[i]`: например, `details[i].amount`.
  Это обозначение для конструктора, а не синтаксис обращения к данным рендерера.
- `schema` содержит типы, русские `title` и обезличенные `example`.
  Пример объекта включает вложенные поля; пример массива — пример элемента.
- Вложенные `$ref` и nullable-ветки раскрываются в структуру `properties`
  для простого обхода на frontend; ограничения и nullable-семантика сохраняются.
- Для навигации конструктора добавляются служебные свойства наподобие
  `details[i]`. Они существуют только в описании: реальный `document_data`
  содержит обычный массив `details`.
- Плоский список путей строится до добавления служебных alias-свойств,
  чтобы не получать дубли.
- Эндпоинт не читает бизнес-данные из БД, не скачивает файл и не вызывает
  template-service. Аутентификация и проверка права на операцию сохраняются.

В EK LS реестр содержит `act`, `bill`, `parcel_registry`, `parcel`.
Тип `revision` отклоняется с 400 из-за произвольного payload, неизвестный
`entity` — с 422 средствами FastAPI. Эти типы и статусы ошибок не переносятся
автоматически в OK Service. Здесь необходимо определить поддержку каждого
из пяти собственных типов и правила ошибок для Flask API.

## Связь схемы и реальных данных

Для каждого поддержанного типа требуется реестр «тип → модель DTO для печати».
И `document_data`, и справочник параметров опираются на один контракт:
нельзя независимо поддерживать произвольный список строк и другой сериализатор.
Объявленное поле должно существовать в контракте сериализатора; допустимость
`null`, пустого списка и отсутствующих данных определяется моделью документа.
Наличие поля в справочнике не означает, что оно заполнено у каждой сущности.

В референсе JSON Schema строится из Pydantic-модели в режиме сериализации,
затем обогащается русскими названиями, рекурсивными примерами и метаданными
по полному пути поля. При построении путей обходятся свойства объекта;
для массивов обход продолжается по `items` с добавлением `[i]` к префиксу.
При переносе нужны и обход, и обогащение схемы; одного списка путей недостаточно.

В OK Service уже используются dataclass DTO и marshmallow. Выбор генератора
JSON Schema должен учитывать существующий стек; этот документ не вводит
обязательную зависимость от Pydantic и не разрешает перенос DTO другого домена.

## Границы слоёв OK Service

- Domain: типы документов и согласованные предметные ограничения.
- Use-case: доступ к исходным данным, выбор шаблона, сборка DTO и поток генерации;
  обращения к БД, S3, рендереру и attachments выполняются через порты.
- Adapters: загрузка бизнес-данных, S3/presigned URL, HTTP-клиент и работа
  с конкретным форматом схемы/внешнего ответа.
- Web: транспортная валидация, аутентификация, вызов сценария и HTTP-ответ.

Конкретное размещение общих функций построения справочника выбирается при
реализации с соблюдением [ARCHITECTURE.md](../ARCHITECTURE.md): use-case
не импортирует Flask, ORM или конкретные адаптеры.

## Что согласовать перед реализацией

1. Данные каждого из пяти типов: исходные сущности/выборки, поля, связи,
   фильтрация, порядок строк, расчёты, nullable-поля и формат дат/чисел.
2. Права генерации и доступа к данным; применимость текущих ролей справочника
   `admin`/`manager` к будущим операциям и их ownership-ограничения.
3. Выбор шаблона: явный ID, дефолтный шаблон, проверка типа и ошибка при
   отсутствии подходящего шаблона.
4. Контракт `output_file_name`, подстановки в имя, расширение и поведение
   при отсутствии настройки; доступные переопределения запроса.
5. Сохранение результата: требуется ли attachment, к какой сущности,
   как обрабатывать повторную генерацию и совпадение имён.
6. Адрес и версия внешнего API, API-ключ, timeout, lifecycle клиента,
   срок действия presigned URL и маппинг ошибок; совместимость старого endpoint.
7. Поля, русские названия, примеры, права и ошибки справочника параметров,
   а также поведение для типов, чья модель данных ещё не определена.

До определения этих правил не формировать бизнес-DTO на основании одних
названий типов или структуры ORM-моделей.

## Проверки будущей реализации

Потребуются тесты соответствия сериализатора справочнику, вложенных путей,
массивов и alias-свойств, русских названий и обезличенных примеров, nullable
и пустых значений. Отдельно — доступ к исходным данным, выбор шаблона,
сохранение явного `false`, payload HTTP-адаптера, ошибки сервиса,
имя/MIME результата и сохранение в attachments, если оно будет предусмотрено.
