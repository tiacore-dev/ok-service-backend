# Расход смены по материалам спецификации

## Контракт и связи

`shift_report_materials.project_material` — обязательный FK на
`project_materials.project_material_id` (`NOT NULL`). Прямая колонка `material`
и ORM-связь расхода с `materials` удалены. Справочный материал доступен через
`project_materials.material`; единица измерения определяется по нему.

`POST /shift_report_materials/add` принимает обязательные `shift_report`,
`project_material`, `quantity` и необязательный `shift_report_detail`.
`PATCH /shift_report_materials/{id}/edit` поддерживает частичное изменение этих
полей; `project_material: null` запрещён. В ответах `view`/`all` возвращается
обязательный UUID `project_material`; поля `material` больше нет.
Фильтр списка — `project_material`, старый фильтр `material` удалён из схемы.
При передаче устаревшего ключа `material` API возвращает `400` с ошибкой
этого поля, даже если одновременно передан `project_material`. Молчаливое
игнорирование запрещено; остальные неизвестные параметры исключаются как раньше.
Права и роли не меняются.

Переданная строка спецификации должна существовать и относиться к проекту смены.
Если передана деталь, она должна относиться к той же смене, а её `project_work`
должен совпадать с `project_work` материала спецификации. Ошибки дают `400`.
Без детали расход можно создать, явно указав материал спецификации проекта смены.
Количество должно быть положительным. Для `шт.` количество приводится к целому
вниз; результат должен оставаться положительным, включая PATCH только количества.

## Автоматическое создание расхода

При создании или изменении детали сохраняется формула:
количество работы детали умножается на норму из `work_material_relations`.
Для единицы `шт.` результат округляется вниз до целого, как до перехода.

Строка спецификации подбирается по проекту смены, справочному материалу нормы
и `project_work` детали; деталь должна принадлежать той же смене.
При нескольких совпадениях выбирается самая ранняя строка по `created_at ASC`,
при равном времени — по `project_material_id ASC`.

Если хотя бы для одного материала нормы подходящей строки нет, операция
создания/редактирования детали целиком отклоняется с `409`. Транзакция
откатывается вместе с изменением количества детали и её расхода. Материал
не пропускается и строка спецификации автоматически не создаётся.
Если норм материалов у работы нет, расход не создаётся, операция разрешена.

При попытке перенести смену в другой проект существующий расход должен
сохранять соответствие проекту; иначе перенос отклоняется с `409` без удаления
расхода. Перенос несопоставленных записей обсуждается отдельно в разделе миграций.

## Миграции

Согласован вариант Б: несопоставленный расход не удаляется. Если после
автоматического сопоставления остаются записи без строки спецификации,
переход на обязательную связь блокируется до ручного разбора данных.

`20261019140000` добавляет временную nullable-связь и заполняет её по проекту
смены, материалу расхода и `project_work` детали, выбирая самую раннюю строку.
Она сохранена как отдельный этап для баз, где уже применялась.

`20261019150000` повторно подбирает соответствия у записей с `null`, затем
проверяет остаток до установки `NOT NULL` и удаления колонки `material`.
Если остаток есть, PostgreSQL выдаёт ошибку с общим количеством и первыми
20 UUID расхода в порядке возрастания. Проверяются все записи независимо от
подписания/удаления смены. Без детали, без `project_work` или без соответствия
запись остаётся несопоставленной; новые строки спецификации не создаются.
Существующая ненулевая связь сохраняется, в том числе установленная вручную.

Alembic выполняет миграции в транзакции PostgreSQL: ошибка откатывает изменения
текущего запуска, включая повторное сопоставление. Если `20261019140000` уже
применена отдельно, база остаётся на этом этапе. При прямом `alembic upgrade head`
откатываются оба новых этапа. Данные расхода не удаляются. Новую версию backend
можно запускать только после успешного завершения миграций.

Для полного списка несопоставленных записей на этапе `20261019140000`:

```sql
SELECT sm.shift_report_material_id,
       sm.shift_report,
       sr.project,
       sm.material,
       sm.shift_report_detail,
       detail.project_work,
       sm.quantity
FROM shift_report_materials AS sm
JOIN shift_reports AS sr ON sr.shift_report_id = sm.shift_report
LEFT JOIN shift_report_details AS detail
    ON detail.shift_report_detail_id = sm.shift_report_detail
WHERE sm.project_material IS NULL
ORDER BY sm.shift_report_material_id;
```

Если общий запуск откатил первый этап, для диагностики можно отдельно выполнить
`alembic upgrade 20261019140000`, сохраняя прежнюю версию backend до завершения
перехода. Затем разобрать полный список, восстановить корректные исходные связи
для автоматического подбора либо явно заполнить `project_material` после проверки
проекта, материала и работы детали по контракту выше. Для расхода без детали
допустима явная связь с материалом проекта смены. После ручного сопоставления
повторить `alembic upgrade head`. Автоматический подбор по-прежнему выбирает
самую раннюю строку по `created_at`, затем UUID. UUID, количество и аудит
расхода сохраняются.

Downgrade второй миграции восстанавливает `material` по связанной строке
спецификации и разрешает `null` у `project_material`, сохраняя все записи
расхода. Downgrade первого этапа удаляет временную связь и индексы.

## Синхронизация спецификации и защита использованных строк

При изменении работы проекта материалы больше не удаляются целиком с последующим
созданием новых UUID. Для каждого материала нормы используется самая ранняя
существующая строка: обновляются количество и `summ = quantity * price`, сохраняются
UUID, название, цена и аудит. При отсутствии цены сумма остаётся `null`.
Недостающие строки создаются. Дополнительные строки того же материала сохраняются.
Если в нормах несколько строк одного материала, существующие строки используются
последовательно в порядке `created_at`, затем UUID; недостающие создаются.

Строки материалов, которых больше нет в нормах работы, удаляются только если
не используются расходом. FK с `NO ACTION` запрещает удаление используемой строки,
в том числе при синхронизации и удалении работы проекта. API возвращает `409`,
изменения транзакции откатываются; расход не удаляется и не отвязывается.

У используемой строки запрещено менять `project`, `material` и `project_work`
(ответ `409`), в том числе переносом работы проекта через синхронизацию.
Количество, цена и название остаются редактируемыми. Строка блокируется
от конкурентного удаления или изменения связей до завершения записи расхода.

## Статистика и развёртывание

Сметная сумма расхода равна количеству, умноженному на текущую цену связанного
`project_material`. При отсутствующей цене сумма равна нулю; количество учитывается.
Статистика учитывает подписанные неудалённые смены. Внешняя группировка
по справочному `material_id` сохраняется: материал берётся через спецификацию.
Это относится и к помесячной статистике прорабов.

Перед запуском новой версии выполнить `alembic upgrade head`. После миграции
прогреть Redis командой
`flask --app app:create_app rebuild-project-material-statistics`: существующий
workflow деплоя уже выполняет её. Новых настроек окружения нет.
