# Правила прав доступа

Этот документ фиксирует текущую модель авторизации и точки, где должны жить проверки прав при переходе к чистой архитектуре.

## Базовый принцип

Есть три разных уровня контроля:

1. аутентификация запроса;
2. грубая проверка роли;
3. проверка прав на конкретный сценарий или конкретную сущность.

Их нельзя смешивать в один "if role == ...", иначе права начинают расползаться по роутеру и теряют предсказуемость.

## Текущие механизмы

### `api_key_or_jwt_required`

Этот декоратор:

- пропускает JWT-запросы;
- пропускает API key-запросы только при наличии права на текущий HTTP-роут;
- поднимает контекст `g.auth_via_api_key`;
- кладёт идентичность API key в `g.api_key_identity_json`.

Если запрос идёт по API key, `admin_required` должен не ломать этот сценарий и пропускать его как технически доверенный.

### `admin_required`

Используется для операций, доступных только администратору.

Если пользователь не `admin`, ответ должен быть `403 Forbidden`.

### `user_forbidden`

Используется там, где пользовательская роль не должна выполнять сценарий.

Это не полная модель авторизации, а грубый HTTP-gate для legacy-роутов.

## Правила для legacy-роутов

1. Если проверка зависит только от роли и не связана с бизнес-сущностью, её можно держать в web-слое как декоратор.
2. Если проверка зависит от ownership, проекта, лидера, статуса или состава сущности, это бизнес-правило и ему место в use-case или domain policy.
3. Роутер не должен сравнивать несколько таблиц и принимать итоговое бизнес-решение, если это можно вынести в сценарий.
4. Сообщения и HTTP-статусы должны оставаться совместимыми с текущим API, пока срез ещё не переведён.

## Ownership и project-leader

Для текущего кода есть отдельный класс проверок:

- может ли `project-leader` работать только со своими проектами;
- может ли он редактировать или удалять только свои `project_works`;
- можно ли ему менять signed-состояние;
- может ли он видеть или трогать данные, относящиеся к чужому проекту.

Такие проверки нужно трактовать как сценарные, а не как "обычный role check".

При миграции в clean architecture:

- transport-layer декоратор оставляем только для грубой авторизации;
- ownership-check переносим в use-case или domain policy;
- репозиторий не должен решать, есть ли у пользователя право на действие.

Для срезов вроде `shift_reports` и `shift_report_details` это означает:

- роутер только достаёт текущего пользователя и нормализует вход;
- use-case решает, можно ли трогать конкретный отчёт или его детали;
- при добавлении новых сценариев не дублировать проверку ownership в нескольких endpoint-ах одного модуля.

### Согласование `shift_reports`

- `PATCH /shift_reports/{id}/sign` не принимает тело запроса и устанавливает `signed=true`;
- согласовать сменный отчёт могут роли `admin`, `project-leader` и `manager`;
- при согласовании сервер заполняет `signed_by` текущим пользователем и `signed_at` текущим Unix timestamp в миллисекундах;
- обычный `PATCH /shift_reports/{id}/edit` не создаёт данные аудита при `signed=true`, но при `signed=false` очищает `signed_by` и `signed_at`.
- После согласования смены (`signed=true`) роли `user`, `project-leader` и
  `manager` могут просматривать смену и связанные вложения/материалы. Вложения
  согласованной смены могут изменять `admin`, любой `manager` и project leader
  текущего project.
- До согласования `user` может добавлять, редактировать и удалять связь с местом
  и удалять вложение собственной смены.
- Для вложений `objects` и `places` просмотр и скачивание доступны любому
  `admin`, `manager`, `project-leader` и `user`; добавление и удаление доступны
  только `admin`.

### Матрица объектов, мест и смен

В текущем API `project` соответствует спецификации из продуктовой матрицы.
`project-leader`, указанный в `projects.project_leader`, является прорабом по
спецификации; любой другой `project-leader` считается прорабом по любой
спецификации.

Пользователь с ролью `user` не имеет доступа к объектам, местам, project-place
связям и чужим сменам. Для операций со сменой доступ пользователя определяется
условием `shift_reports.user == current_user`.

Для связи «смена–место» до согласования (`signed=false`) добавлять,
редактировать и удалять связь могут `admin`, project leader текущего project и
владелец смены с ролью `user`. После согласования (`signed=true`) эти операции
доступны только `admin` и project leader текущего project. Просмотр доступной
смены разрешён `admin`, `manager`, любому `project-leader` и владельцу смены с
ролью `user`. Редактирование project-place связей запрещено всем ролям.

## Проверки для API key

Если endpoint доступен по API key:

- доступ определяется через текущий HTTP method + route;
- права должны быть явно описаны в таблице permission types;
- отсутствие сопоставления означает `403`, а не неявный успех.

## Правила миграции

1. Не переписывать права "на глаз" при переносе среза.
2. Для каждого переведённого endpoint нужно иметь явный тест на allowed и forbidden сценарий.
3. Если право относится к сущности, а не к роли, его нельзя потерять при разнесении по слоям.
4. Если права меняются, это должно быть видно в документации и тестах до удаления старой логики.

## Тестовый gate

Перед тем как брать следующий модуль в переезд, нужно убедиться, что:

- есть тесты на happy path;
- есть тесты на forbidden path;
- есть тесты на edit/create contract;
- есть тесты на list/filter contract;
- для изменённого среза пройдены unit-тесты без БД, а при наличии окружения - и интеграционные pytest-сценарии.

Если тесты не покрывают новый контракт, следующий срез лучше не начинать.
