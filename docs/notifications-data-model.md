# Модель данных уведомлений

Реализованы application-сценарии атомарного создания уведомления с одним или
несколькими получателями и фиксации первого просмотра. Создание через эти
сценарии выполняется транзакционно: общая запись и персональные записи либо
сохраняются все вместе, либо откатываются. Повторяющиеся ID получателей в одной
команде схлопываются. Повторный вызов отметки просмотра сохраняет timestamp и
browser ID первого успешного вызова. Проверка принадлежности выполняется по
связи с текущим user ID; отсутствующая персональная запись возвращает `None`.

Уникальность пары уведомление/получатель предотвращает дубли получателей
внутри одной общей записи. Повторные команды создания дедуплицируются по
`idempotency_key`. Каждая новая команда создания требует этот ключ — стабильный
ключ источника операции, например `shift_report.signed:<status-history-uuid>`. Для
разных реальных событий одной сущности вызывающий сценарий передаёт разные ID
событий; ключ не выводится из ID сущности или текста. PostgreSQL обеспечивает
уникальность ключа. Повтор с тем же ключом и тем же содержимым и набором
получателей возвращает исходную запись без новых получателей. Повтор ключа с
другим типом, текстом, ссылкой, автором или набором получателей вызывает
`NotificationIdempotencyConflictError`; сохранённые данные не меняются.

Поле ключа nullable для строк, созданных до миграции, но application-сценарий
требует ключ для каждого нового создания.

Use-case чтения предоставляет историю, непросмотренный список, счётчик и
получение одной записи. Репозиторий всегда ограничивает их `user_id` текущего
сценария. История сортируется по `created_at DESC, notification_id DESC`; offset
и limit дают воспроизводимый порядок при одинаковых timestamp. Пользовательская
и административная HTTP-схемы ответа не содержат `browser_id`.

HTTP API истории и устройств описан в [контракте](./notification-api.md).
Push-доставка выполняется отдельным worker; массовая административная рассылка
описана в контракте HTTP API. Подключённые события смен перечислены ниже.

## Сущности

- `notifications` хранит общие данные события или рассылки: тип, заголовок,
  текст, время создания, необязательную ссылку и необязательную пару типа/ID
  связанной сущности. `created_by` может указывать на инициатора; удаление
  пользователя оставляет уведомление, очищая ссылку на автора.
- `notification_recipients` хранит персональное состояние для пользователя.
  Уникальность пары уведомление/пользователь не позволяет создать дубль.
  `viewed_at` и `browser_id` заполняются при фактическом просмотре; отправка push
  не меняет эти поля. Для непросмотренной записи оба поля должны быть `NULL`, а
  просмотренная запись должна содержать оба значения.

Для массовой рассылки одна запись `notifications` связывается с отдельными
записями получателей. `notification_type` — строковый ключ, перечень значений
задаётся вызывающими сценариями в последующих этапах. `related_entity_type` и
`related_entity_id` хранят ссылку без полиморфного внешнего ключа; ссылочная
целостность конкретной сущности проверяется в прикладном сценарии.

Текущий индекс получателей `(user_id, viewed, notification_id)` подходит для
выборки непросмотренных/просмотренных записей пользователя, а индекс
`notifications(created_at, notification_id)` — для глобальной сортировки.
Совместно они не обеспечивают сортировку персональной истории по времени после
join: PostgreSQL, вероятно, потребуется сортировать выбранные строки. Перед
введением API истории следует проверить план на ожидаемом объёме; если сортировка
станет узким местом, рассмотреть сохранение `created_at` в записи получателя с
индексом `(user_id, created_at, notification_id)`.

Жёсткое удаление пользователя сейчас каскадно удаляет его персональные записи;
мягкое удаление сохраняет их. Если продукт требует сохранять историю после
физического удаления, потребуется отдельное решение об обезличенном получателе
или снимке идентичности и миграция FK/данных.

Время хранится в Unix epoch milliseconds согласно общему контракту проекта.

## События смен (OK-45)

| Событие | Точка интеграции | Получатель | Заголовок / текст |
| --- | --- | --- | --- |
| `shift_report.created` | успешное одиночное или массовое создание | `shift_reports.user` | «Назначена смена» / «Вам назначена смена №N.» |
| `shift_report.approved` | `/shift_reports/{id}/sign`, первое согласование после снятия признака или первая явная подпись без аудита | `shift_reports.user` | «Смена согласована» / «Смена №N согласована.» |
| `shift_report.opened` | успешный `/shift_reports/{id}/start` | `projects.project_leader` связанной спецификации | «Смена открыта» / «Смена №N открыта.» |
| `shift_report.closed` | успешный `/shift_reports/{id}/finish` | `projects.project_leader` связанной спецификации | «Смена закрыта» / «Смена №N закрыта.» |

В текущей модели спецификация имеет не более одного прораба; если
`project_leader` отсутствует, уведомление и задания доставки не создаются.
Резервного получателя нет. Назначение читается при событии в той же транзакции,
а затем сохраняется в персональной записи; последующее изменение назначения не
перенаправляет уже созданное уведомление. FK смены и спецификации гарантируют
наличие связанной записи пользователя; мягкое удаление пользователя сохраняет
персональную историю по общим правилам уведомлений. Действующая push-подписка
не обязательна для сохранённого уведомления. Ссылки frontend не заданы: маршрут
не подтверждён в этом репозитории.

Уведомление, получатель и задания для активных session-bound подписок создаются
в транзакции изменения смены; при ошибке все эти изменения откатываются.
Firebase вызывается только worker после фиксации. При массовом создании все
смены и их уведомления фиксируются вместе. Для создания ключ содержит UUID
смены; создание не имеет ключа запроса: каждый успешный запрос создаёт новую
смену и событие, включая повтор идентичного запроса. Для каждой новой успешной
подписи, открытия и закрытия создаётся UUID события и сохраняется в уникальном
ключе уведомления. Проверка состояния под блокировкой строки смены не позволяет
повторной или конкурентной операции создать второе уведомление для того же
перехода; после внешнего сброса состояния новый переход получает новый UUID.
Отдельная таблица истории переходов и миграция не нужны. Без назначенного
получателя UUID и уведомление не сохраняются. Изменения через обычный edit и
начальные значения полей создания не являются отдельными событиями подписи,
открытия или закрытия. Повторный sign сохраняет прежнее поведение обновления
аудита, но повторное уведомление не создаёт. Уникальный ключ и ограничения
получателей/доставки обеспечивают дедупликацию записей, но не гарантируют
единственную внешнюю доставку Firebase при повторных попытках worker.

### Проверка на dev только средствами backend

После отдельного согласования развёртывания использовать тестовых пользователей
и тестовую спецификацию в статусе `in_progress`, назначить ей `project_leader`.
Создать смену через `POST /shift_reports/add`, затем выполнить `start`, `finish`
и `sign` с разрешёнными JWT и корректными координатами. Через персональный
`GET /notifications` каждого тестового пользователя проверить тип, текст и
принадлежность; повторить `sign` и убедиться, что нового уведомления нет, а
повторный `start`/`finish` возвращает конфликт. Для спецификации без прораба
проверить отсутствие уведомления о start/finish. При наличии активной тестовой
подписки проверить соответствующие строки `push_deliveries` и состояние worker;
без подписки сохранённое уведомление всё равно присутствует. Токены устройств и
содержимое учётных данных в запросы диагностики и журналы не выводить. Реальный
Firebase и браузер для проверки сохранения записей не обязательны.
